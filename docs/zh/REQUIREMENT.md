# 需求分析文档 — Backup Manager

## 1. 产品概述

| 项目 | 内容 |
|------|------|
| 产品名称 | Backup Manager（备份管理器） |
| 产品定位 | 文件/目录聚合备份可视化管理软件 |
| 一句话描述 | 基于 Git 的反向追踪模式（白名单机制），通过软链接聚合管理源文件，并提供可视化界面的备份管理工具。 |
| 核心价值 | 让用户以"指定要备份什么"（而非"排除什么"）的直观方式管理备份，同时提供可视化操作界面，降低备份管理门槛。 |

### 1.1 核心设计理念

**反向追踪模型**：与 `.gitignore` 的"排除模式"相反，用户主动指定哪些文件/目录需要被追踪备份，未被指定的文件自动忽略。类似于一个白名单系统。

**条目与链接聚合**：备份仓库（repo）的真实内容存放在 `data/` 下。**条目（Entry）** 就是 `data/<repo_path>` 下被备份的某个文件或目录 —— 它就是白名单里的一条。**链接（Link）** 则是绑定到该条目的一个本机路径，形态是指向 `data/` 的软链接。所有链接**完全等价**：通过任何一条编辑都是对同一份内容的同一个操作，因此模型里不存 in/out 之分。

**前后端一体**：系统采用前后端一体架构，单进程一键启动，无需分别部署前端和后端服务。

### 3.2 条目与链接管理（data/）

**条目**是 `data/<repo_path>` 下被备份的一个文件/目录。**链接**把本机路径绑定到条目；一个条目可以有 **0..N 条链接**。由于每条链接都是指向同一 `data/<repo_path>` 的软链接，它们**完全等价** —— 没有主链接、没有跟踪链接、也没有需要切换的东西。没有链接的条目合法：内容在仓库里，只是本机没有视图。

| ID | 功能 | 描述 | 优先级 |
|----|------|------|--------|
| FR-5 | 创建条目（adopt） | 用户选择本机文件/目录及 `data/` 下的目标路径。目标路径既可手动填写，也可通过范围严格限制在 `data/` 内的可视化父目录选择器回填；使用选择器时，系统自动追加且保留源对象名称。“显示隐藏文件”开关控制是否展示以点号开头的目录。选择器可添加待创建子目录，这些目录仅在确认 Adopt 时实际创建。随后内容被**移动**到 `data/<repo_path>`，原位置被替换为软链接，条目与其第一条链接同时创建 | P0 |
| FR-6 | 查看条目与链接列表 | 按 `repo_path` 分组展示所有条目，可展开查看其链接、所属设备与每条链接的状态 | P0 |
| FR-7 | 添加链接 | 把条目分发到另一个本机路径（创建指向 `data/<repo_path>` 的软链接）。本机完整路径既可手动输入，也可通过可视化目录选择器选择父目录并追加条目名称；条目的链接数量不限，**尚无链接的条目也可以添加** —— 这正是新设备为「仓库中已存在的内容」建立绑定的方式 | P0 |
| FR-9 | 批量链接 | 选择多个条目与一个本机根目录，为每个条目在 `<local_root>/<repo_path>` 创建链接 | P1 |
| FR-10 | 链接状态诊断与修复 | 诊断每个链接（`ok` / `missing` / `wrong_target` / `replaced` / `dangling` / `occupied` / `disabled`），并提供创建 / 修复 / 重新纳入 | P0 |
| FR-11 | 一致性巡检 | 校验各项不变量（链接只绑定完整条目、绝不绑定子路径；条目之间不重叠；链接不在目录条目内部；`data/` 内无软链接、没有引用未登记设备）并报告未托管链接；可一键修复所有可收敛项 | P1 |
| FR-25 | 移除链接 / 条目 | 移除单个链接（安全；条目与内容都保留）；或以条目为单位移除：`unlink`（仅本机链接）/ `move_back`（内容回到指定本机路径）/ `purge`（删除内容） | P0 |

**一致性规则（必须成立）**：链接必须与被备份的文件/目录保持完全一致。若某个目录被跟踪，则该目录内的任何单个文件都不允许再建链接。因此条目之间永不重叠，链接永远绑定完整条目。

### 3.3 多设备管理

**设备**是引用该仓库的一台机器，以稳定的机器指纹标识。设备是元数据，链接是它的子数据。

| ID | 功能 | 描述 | 优先级 |
|----|------|------|--------|
| FR-26 | 设备注册 | 检测当前机器指纹并自动在仓库中注册（名称默认取 hostname，可重命名）；列出所有设备及其链接数 | P0 |
| FR-27 | 应用设备（apply） | 让本机收敛：先展示 dry-run 计划（create / repair / skip / conflict / orphan），确认后执行。绝不覆盖已被占用的路径。没有 create/repair 动作时直接关闭计划，不发送执行请求；即使直接调用执行接口，no-op 也不会重写清单 | P0 |
| FR-28 | 卸载设备（detach） | 删除本机软链接（`unlink`）或仅停止管理（`keep`）。从不触碰 `data/`。定义保留，因此重新挂载只需一次 Apply | P1 |
| FR-29 | 删除设备 | 删除设备的链接定义。条目本身保留 —— 一条链接都不剩的条目合法 | P1 |

## 5. 核心概念 / 数据模型

### 5.1 目录结构

```
<repo-root>/
├── .backup-manager/
│   └── manifest.json    # 设备 + 条目 + 链接（Git 跟踪，唯一事实来源）
├── data/                # 真实内容 —— 唯一的内容存放处
│   ├── documents/
│   │   ├── report.docx
│   │   └── notes.txt
│   └── config/
│       └── settings.json
└── .git/                # Git 版本库

本机侧 —— 每个链接都是指向仓库的软链接：
  ~/Documents/report.docx  ->  <repo>/data/documents/report.docx
  ~/Desktop/notes.txt      ->  <repo>/data/documents/notes.txt
  ~/Desktop/report.docx    ->  <repo>/data/documents/report.docx
```

### 5.2 核心实体

```
BackupRepo
├── id: string
├── name: string
├── path: string          # repo 根目录绝对路径
├── createdAt: timestamp
├── updatedAt: timestamp
├── lastBackupAt: timestamp|null
├── status: 'active' | 'error' | 'backing_up'
├── config:
│   ├── remoteUrl: string
│   ├── branch: string (default: main)
│   ├── autoBackup: boolean
│   ├── autoBackupInterval: string (cron 表达式)
│   ├── gitUserName: string
│   └── gitUserEmail: string
└── entries: Entry[]
    └── links: Link[]

Entry                          # 一个被备份的文件/目录
├── id: string
├── repoPath: string           # 在 data/ 下的路径 —— 内容的身份
├── kind: 'file' | 'dir'
├── createdAt: timestamp
└── links: Link[]              # 0..N 条链接，全部完全等价（无 in/out 类型）

Link                           # 绑定到条目的一个本机路径
├── id: string
├── entryId: string
├── device: string             # 设备指纹
├── localPath: string          # 软链接的本机绝对路径
├── enabled: boolean
└── createdAt: timestamp

Device                         # 一台机器的元数据
├── fingerprint: string        # 稳定机器标识（十六进制 sha256）—— 主键
├── name: string               # 默认取 hostname，可重命名
├── hostname, os: string
└── lastSeenAt: timestamp
```

### 5.3 持久化

共有**三份彼此独立的存储**，文件、格式与存在理由各不相同：

| 数据 | 文件 | 格式 | 为什么放这里 |
|------|------|------|------|
| `repos`、`repo_configs`、`repo_auths` | `~/.config/backup-manager/backup-manager.db` | SQLite（二进制） | 本机私有：含加密凭据、本机路径、定时任务。绝不提交 |
| 条目、链接、设备 | `<repo-root>/.backup-manager/manifest.json` | JSON，Git 跟踪 | 必须跨机器传输。SQLite 文件按机器独立，传不过去 |
| 应用设置 | `~/.config/backup-manager/config.json` | JSON | 应用级设置，包括应用范围的 `language`（默认 `en`） |

**SQLite 数据库** —— `~/.config/backup-manager/backup-manager.db`，三张表（不变）：

```sql
repos         — 仓库: id, name, path, created_at, updated_at, last_backup_at, status
repo_configs  — 配置: repo_id(FK), remote_url, branch, auto_backup, auto_backup_interval, git_user_name, git_user_email
repo_auths    — 认证: repo_id(FK), auth_type, ssh_private_key(BLOB), ssh_private_key_path, username, password_encrypted(BLOB)
```

旧的 `symlinks` 表已删除，也没有新表替代它 —— 条目、链接与设备**不**存放在 SQLite 中。

**仓库清单** —— `<repo-root>/.backup-manager/manifest.json`，位于仓库内的 JSON 文件：

```json
{
  "version": 1,
  "updated_at": "2026-09-18T10:00:00Z",
  "devices": [
    { "fingerprint": "9f2c…", "name": "MacBook Pro", "hostname": "mbp.local",
      "os": "darwin", "last_seen_at": "2026-09-18T10:00:00Z" }
  ],
  "entries": [
    { "id": "e1a2…", "repo_path": "documents/notes.txt", "kind": "file",
      "created_at": "2026-09-01T08:12:00Z",
      "links": [
        { "id": "l1a2…", "device": "9f2c…",
          "local_path": "/Users/x/Documents/notes.txt", "enabled": true,
          "created_at": "2026-09-01T08:12:00Z" },
        { "id": "l2b3…", "device": "9f2c…",
          "local_path": "/Users/x/Desktop/notes.txt", "enabled": true,
          "created_at": "2026-09-10T12:00:00Z" }
      ] }
  ]
}
```

条目、链接与设备之所以存放在仓库内而不是 SQLite，是因为数据库是按机器独立的。把它们放进仓库（由 Git 版本化并传输），另一台机器才能仅凭 `git clone` 就获知所有设备的链接。

## 6. 用户确认的关键决策

| 问题 | 决策 |
|------|------|
| Git 远程仓库 | `git push` 为可选项。未配置远程仓库时只做本地 commit 不 push |
| **内容归属** | 内容**只**存在于 `data/<repo_path>`。本机路径不是第二份副本，而是指向它的软链接视图 |
| **链接等价** | 每个条目有 0..N 条链接，且全部等价 —— 同一目标、同一语义。没有 `in`/`out` 类型、没有跟踪链接、没有需要切换的东西 |
| **链接一致性** | 链接始终绑定完整条目。跟踪某个目录时，禁止对该目录内的文件建链接；条目之间永不重叠 |
| **条目即白名单成员** | 条目存在于清单中就是「被备份」的定义。没有链接的条目合法 —— 内容在仓库里，只是本机没有视图 |
| **设备元数据位置** | 设备、条目与链接存放于仓库内的 `<repo>/.backup-manager/manifest.json`（Git 跟踪），而非按机器独立的 SQLite，从而新机器仅凭 `git clone` 即可获知 |
| **Adopt 语义** | 创建条目会把源文件**移动**进仓库并用软链接替换原位置。原文件绝不留存为第二份副本 |
| 内容删除 | 删除内容需输入 `repo_path` 二次确认；提供 `unlink` / `move_back` 作为非破坏性替代；每次删除前先提交，因此 `git revert` 永远可用 |
| 前端技术选型 | React 18 + TypeScript + Vite + Ant Design 5 + i18next/react-i18next；Ant Design 与 dayjs 使用活动 UI 语言环境 |
| UI 语言 | 支持 `en` 与 `zh-CN`，默认 `en`，所选应用级默认语言持久化到 `config.json` |
| 启动方式 | 启动后自动打开浏览器 |
| Markdown 图片 | 支持 Markdown 中的本地图片显示 |
| 多仓库 | 支持多个仓库并行管理 |
| 后端框架 | Gin（Go 轻量高性能 HTTP 框架） |
| 数据库 | SQLite（纯 Go 实现 modernc.org/sqlite，无需 CGO） |
| 认证加密 | SSH 私钥和 HTTPS 密码使用 AES-256-GCM 加密存储 |
| 内容回滚 | 回滚会覆写 `data/`（需要用户确认），回滚前展示变更文件列表。所有本机链接会立即反映回滚结果 |
| 仓库删除 | 删除仓库仅移除数据库记录和调度任务，保留文件系统上的数据不丢失 |
| **预览/编辑目标** | 预览与编辑操作的对象是 `data/<repo_path>` —— 只写一次，不再向独立的源文件双写 |
| **向后兼容** | 不要求兼容。旧的 `symlinks` 表与 `.links/` 目录会被删除；`data/` 内容保留 |

## 7. 预览与编辑功能需求详情

### 7.1 功能描述

仓库详情页的浏览（Browse）标签页会在 `data/` 目录树中显示点号开头的文件和目录，确保所有已备份对象均可见。用户选择节点后，可实现：
- **纯文本文件**：查看文件内容（只读预览），并可切换至编辑模式修改后保存
- **Markdown 文件**：在渲染预览模式与原始文本编辑模式之间切换，编辑后保存
- **二进制文件**：仅显示文件类型信息，不可编辑

普通文本和 Markdown 的预览/编辑区随浏览（Browse）标签页的剩余可用高度展开。

### 7.2 操作对象说明

| 操作 | 对象 | 说明 |
|------|------|------|
| 预览（读取） | `data/<repo_path>` | 读取该条目的内容展示给用户 |
| 编辑（保存） | `data/<repo_path>` | 就地写入。该条目的每个链接都会立即反映变更，因为它们都是指向同一文件的软链接 |
| 备份 | `data/` | `git add -A` 即收录改动 —— 不存在增量同步步骤 |

### 7.3 与备份的关系

编辑不会自动触发备份。改动以未提交的工作区变更形式停留在 `data/` 中，由下一次手动或定时备份收录。备份（Backup）标签页会展示未提交变更数量，作为「有新变更」的提示。这是合理的设计 —— 编辑是独立行为，备份时机由用户自主控制。

由于所有链接背后是同一个文件，通过任意链接编辑、或在 Browse 标签页编辑，都是对同一内容的同一次操作。
